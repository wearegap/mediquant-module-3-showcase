# MAF Showcase (Module 3, trainer repository)

Minimal console code that shows each Module 3 concept in isolation. One branch per session, cumulative:
`session-5` (this content), `session-6`, `session-7`, `session-8`.

Fictional data only. No real patient data, ever.

## Status of this code

Written against the Microsoft Agent Framework docs and samples as of 2026-10-21.
Module 3 sessions are numbered 5 to 8, after Module 2's sessions 1 to 4.

## Setup (PowerShell or Git Bash)

```bash
dotnet restore src/MafShowcase
dotnet user-secrets set "OpenAI:ApiKey" "<shared key from IT>" --project src/MafShowcase
dotnet run --project src/MafShowcase -- step01
```

Steps: `step01` first agent · `step02` run vs stream · `step03` function tools · `step04` multi-turn session · `step05` interactive console chat (type `/new` to reset the conversation, `/exit` to quit).

Session 6 steps (branch `session-6`): `step06` PHI pseudonymisation · `step07` input and output guards · `step08` tool guard · `step09` tool approval (interactive y/n) · `step10` OpenTelemetry traces to the console (trainer demo).

Session 7 steps (branch `session-7`, run from the repository root): `step11` ingest: load with file-name metadata, chunk (by hand, then side by side with DataIngestion), rebuild `data/protocols.db` · `step12` embeddings, keyword vs semantic, top-k and the threshold, the ward metadata filter · `step13` RAG by hand: the search tool with citations in the guarded assistant · `step14` the same retrieval with the built-in `TextSearchProvider`, both modes. Run `step11` first.

The protocol PDFs in `data/protocols/` are fictional training documents (real medicine names, fictional hospital and local rules). They are generated by `module-3/session-3/_build/protocols.py`. Ward 4B has 8 (the same files the lab uses); Ward 6R (renal) has 3 on the same medicines with different rules, only to demonstrate metadata filters. File names follow `WP-<ward>-<number>-<topic>.pdf`, and the loader reads ward, document id and topic from them.

**Session 3 status:** built, tested and run with the key in rehearsal on 2026-11-02.

Session 4 steps (branch `session-4`): `step15` executors and edges, no AI, with the Mermaid diagram · `step16` fan-out to three checks, fan-in barrier, shared state, supersteps · `step17` feature 0008: two agent steps inside a fixed graph and a RequestPort pause for the nurse (interactive y/n) · `step18` checkpoints: stop while waiting for the nurse, resume in a new workflow instance (trainer only) · `step19` ready-made orchestrations: sequential and concurrent agents. `step17` and `step18` need the index from `step11`.

**Session 4 status:** written 2026-11-02 against the Learn workflow pages and the official samples. **Not compiled or run yet.**

**Session 2 status:** written 2026-10-26 against the Learn pages for agent middleware, tool approval, structured outputs and observability. **Not compiled or run yet.** Rehearsal checks: build, `dotnet test`, then run steps 06 to 10 with the key.

## Tests (no network, no key needed)

Create the test project once, then add the two files already in `tests/MafShowcase.Tests/`:

```bash
dotnet new xunit -o tests/MafShowcase.Tests --force
dotnet add tests/MafShowcase.Tests reference src/MafShowcase
dotnet test tests/MafShowcase.Tests
```

Delete the template's `UnitTest1.cs` after `dotnet new`. `--force` keeps the existing files.

## Layout

| Path | What it shows |
|---|---|
| `Configuration/OpenAISettings.cs` | One `OpenAI` config section; key from user-secrets, model from appsettings.json, fail fast |
| `Agents/WardAssistantFactory.cs` | The only place that builds the chat client and the agent |
| `Tools/WardTools.cs` | Read-only tools with descriptions, explicit snake_case names, delegating to a query layer |
| `Ward/WardQueries.cs` | Stand-in for MedTrack's existing query layer, fictional data |
| `Steps/` | One file per concept, run from `Program.cs` |
| `tests/.../ScriptedChatClient.cs` | Fake `IChatClient` so unit tests never call OpenAI |
| `Agents/GuardedWardAssistantFactory.cs` | Session 6: the whole guardrail stack, composed in the order a request travels |
| `Guardrails/PseudonymMap.cs`, `PseudonymisingChatClient.cs` | Chat client middleware: names and MRNs become placeholders on every model call and are restored on the way back |
| `Guardrails/InputGuard.cs`, `OutputGuard.cs`, `RunGuardrails.cs` | Agent run middleware: a classifier with structured output before the run, deterministic checks after it |
| `Guardrails/ToolGuard.cs`, `AdministrationValidator.cs` | Function middleware: argument checks on every tool call, after any approval |
| `Tools/RecordingTools.cs`, `AdministrationDraft.cs` | The one write tool, wrapped in `ApprovalRequiredAIFunction`; the draft as a typed contract |
| `Ward/AdministrationRecorder.cs` | Stand-in for MedTrack's existing recording handler, and `WardContext`: everything the server fixes |
| `Guardrails/WireTapChatClient.cs` | Showcase only: prints what actually leaves the process |
| `Rag/PdfLoader.cs`, `Chunker.cs` | Ingestion without AI: text per page with PdfPig, metadata from the file name, boilerplate removed, sentence-aware chunks with whole-sentence overlap |
| `Rag/ProtocolIndex.cs` | The SQLite vector store with automatic embedding: rebuild (wipe, chunk, upsert; the store embeds) and search (optional ward filter, top-k, threshold) |
| `Tools/ProtocolTools.cs` | `search_ward_protocols`: retrieval as an ordinary read-only tool, filtered to the conversation's ward, with citations and an explicit "not found" |
| `Workflows/RoundExecutors.cs` | Plain C# executors (find patient, find due order, three checks, the fan-in aggregator) and the step 15 and 16 graphs |
| `Workflows/AdministrationReviewWorkflow.cs` | Feature 0008: Drafter agent, order check and protocol-check agent in parallel, review card, RequestPort sign-off, recorder |
| `tests/.../WorkflowTests.cs` | The graphs tested like code: sequential output, fan-in, approve, reject, never offered, no PHI to the model |
| `tests/.../HashingEmbeddingGenerator.cs`, `RagTests.cs` | A fake embedding model and retrieval tests against the real PDFs |
| `tests/.../GuardrailTests.cs` | Every guardrail proven with the scripted client, including "an approved but invalid draft is still blocked" |
